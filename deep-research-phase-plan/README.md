## Safe parallel-work rules

- Parallelize only tasks that write different artifacts and do not decide the same URL, claim, metric definition, selector, or configuration.
- Read-only inventories may run alongside authorized console exports, but merge them only after labeling repository-local versus external evidence.
- Research for Phase 03 can start after M1 facts are available; final link recommendations wait for M2. Phase 05 inventory can run before field evidence, but pilot selection cannot.
- Never parallel-edit shared surfaces such as `index.html`, `sitemap.xml`, `robots.txt`, `_redirects`, shared navigation, analytics, or locale templates without one named integrator.
- One owner controls the evidence log and decision record for a day. Reviewers may add signed findings rather than silently overwrite observations.
- Use separate branches/worktrees for future implementation; rebase and rerun gates before merging. Documentation research must not be presented as deployed behavior.
- A failed security/privacy gate, conflicting canonical/hreflang decision, or incompatible metric definition stops dependent parallel work.

## Blocking conditions

A decision is blocked—not guessed—when its authoritative evidence is inaccessible; console property/date/filter is unknown; local and deployed observations conflict; a security/privacy test fails; URL ownership or rollback is unresolved; instrumentation is absent; native-language judgment lacks a qualified reviewer; standards/dialect scope is undefined; or another milestone named in the matrix is not accepted.

Block only the dependent decision. Continue safe preparation: inventory repository paths, create synthetic fixtures, write exact console procedures/export schemas, reproduce local behavior, enumerate selectors, or document rollback. Mark current indexing, Google-selected canonicals, analytics/GSC values, demand, field performance, translation quality, deployed request behavior, and outreach outcomes `unknown` or `pending` until their authoritative source is observed.

## Selecting the next unblocked day

1. Start with the earliest incomplete day in the recommended order.
2. Read its prerequisites, evidence contract, and the matrix row for its phase.
3. Confirm each required milestone is accepted and each required source/access/reviewer is available.
4. If fully ready, execute it. If partly ready, do only explicitly safe preparation and mark the handoff `partially unblocked`.
5. If its decision threshold cannot be reached, record the blocker, owner, exact evidence needed, and fallback; then scan forward for the earliest day whose outcome does not consume that missing decision.
6. Never use a later day's assumption to manufacture an earlier milestone. Return when evidence arrives and revalidate downstream work for drift.

## Global guardrails and done definition

- Preserve existing ranking URLs unless authoritative evidence and an approved migration/rollback justify a move.
- Do not mass-create locales or unrelated generic tools.
- Do not claim safe PDF redaction unless the underlying content is demonstrably unrecoverable under the documented threat tests.
- Do not claim files/data remain local until network and implementation evidence supports the exact wording.
- Do not interpret missing GSC/analytics/CrUX/search-demand/native-review/outreach evidence as zero or success.
- A phase exits only when its overview exit criteria and Day 14 milestone handoff are accepted, with unknowns and blockers retained.
